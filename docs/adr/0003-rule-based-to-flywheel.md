# ADR-0003: ルールベース分類からデータフライホイールへの進化設計

- **ステータス**: 採用済み
- **決定日**: 2026-05-23
- **決定者**: Team 10

## 背景

HowTune のコア機能は、AirPods 頭部モーションを 3 状態聴取タグ（groove / chill / neutral）に分類することである。

立ち上げ時点ではラベル付きの学習データが存在しないため、機械学習モデルをゼロから訓練することはできない（コールドスタート問題）。

## 検討した選択肢

| 選択肢 | メリット | デメリット |
|---|---|---|
| **ルールベース → フライホイール** | 初日からデモができる。ユーザー行動を暗黙ラベルとして蓄積できる | 初期精度が低い |
| 事前学習済みモデルのファインチューン | 精度が高い | 音楽×センサーのドメイン特化データセットが存在しない |
| ユーザーに手動でラベル付けさせる | ラベルの品質が高い | UX を損なう。継続率が下がる |

## 決定

**フェーズ1: ルールベース分類**で即座に動くものを作り、**フェーズ2 以降: データフライホイール**で精度を上げていく設計を採用する。

### フライホイールの仕組み

```
AirPods 頭部モーション
  ↓ ルールベースで 3 状態スコア化
反応区間を検出・タグ付け
  ↓
AI 対話（HowChatView）で「この瞬間どう感じた？」と問いかける
  ↓ ユーザーの回答 = 暗黙のラベル
ラベル付きデータが蓄積される
  ↓
3状態 → 32次元 → 128次元 の高次元埋め込みモデルへ進化
  ↓ より精度の高い分類 → より精度の高い問いかけ → ...
```

AI 対話の回答はユーザーに「ラベリングしている」と意識させない形で、学習データとして機能する。

## 結果

- ハッカソン期間内に動作するデモを実現できる
- ユーザーが使えば使うほどモデルが改善する持続的な競争優位を設計できる
- 「AI が聴き方を学習していく」というストーリーがプロダクトのナラティブとして機能する
- MVP 段階でのコールドスタート問題を回避できる

## ロードマップ

| フェーズ | 分類手法 | データ |
|---|---|---|
| MVP（現在） | ルールベース 3状態 | なし |
| Phase 1 | 3状態 → 32次元埋め込み | HowCard 投稿データ |
| Phase 2 | 32次元 → 128次元 | AI 対話ログ + コミュニティデータ |
| Phase 3 | パーソナライズモデル | 個人の聴取履歴 |
